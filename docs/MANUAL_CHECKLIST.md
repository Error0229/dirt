# Manual checklist

What the automated tests cannot see: the parts of each client that only
exist on a real screen, and the glue between the app and the operating
system. Everything else is covered by tests of `dirt-core` and by
`dirt-sim`, which runs real client cores against the real server.

Run it before a release, and after changing anything it names. Record the
run at the end. It is laid out to be walked through by hand, device by
device, each in the order a person meets things: starting and writing,
finding, putting away, syncing, the account, Settings, files, capture from
outside, voice, screen readers. It was rewritten for the new interface in
step 10b of the interface plan; the items keep the numbers they had, which
other documents and earlier runs refer to, so the numbers are not in
order. A15 became part of A2.

**Who.** "Person" marks what no agent can check: what needs a real
microphone, a real phone, a screen reader (Narrator, TalkBack), WebKit on
macOS or Linux, a release build, or acts on the screen, the keyboard, the
browser or the dialogs of a computer somebody is using. The others an
agent can run too, with the stand-ins below, and the runs at the end say
which were.

## Before starting

- A server to test against that is not a live one, with its migrations
  applied. `docs/DEPLOY.md` says how to run one.
- A sign-in that the server's Clerk instance accepts. A development
  instance accepts `<anything>+clerk_test@example.com` with the code
  `424242`.
- For the desktop app and the CLI, set `DIRT_DATA_DIR` to an empty folder,
  so that the run does not touch real notes. They share that folder and one
  keychain entry, named after the server: they are one device.
- The desktop app built with `dx build --platform desktop`. A plain `cargo`
  build runs without its style sheets.
- The Android app on an emulator, and on a physical device when one is to
  hand. Record which.
- A second device in the same account, for the items that sync: the CLI
  on its own data folder will do.

Afterwards, delete the test account, the keychain entry and the app's data.

## Desktop app

A development build kept off the screen with `DIRT_WINDOW_AT` never takes
the keyboard from the app in front, nor flashes in the taskbar: neither its
main window nor quick capture's. With `DIRT_ACTIONS_FROM_STDIN` set, the
lines `hotkey`, `new note`, `open dirt` and `quit` on its standard input
stand in for the hotkey and the tray's menu (the real Ctrl Alt N is then
not registered, so a test run leaves it to the person at the computer), and
`DIRT_TRAY_AT=x,y` (or `none`) for where the tray icon is, so that quick
capture's flight can be tried off the screen. A release build ignores all
three.

A development build listens to a WAV file instead of the microphone when
`DIRT_VOICE_FROM_WAV=<file>` is set: at the pace it was recorded, from its
start each time listening starts, then a quiet room. `DIRT_ACTIONS_FROM_STDIN`
also takes `hotkey down` and `hotkey up`, a held Ctrl Alt N. With the two,
voice can be tried off the screen; the real microphone and the real keys
are D75 to D88's.

A development build has two stand-ins for trying Settings without the
person's browser and dialogs: `DIRT_SIGN_IN_TO_FILE=<file>` writes the
sign-in address to that file instead of opening the browser (open it in a
browser of your own), and `DIRT_EXPORT_TO=<folder>` exports into that
folder without asking. A release build ignores both, so D4 and D10 are
still for a person in a release build.

An agent's run on a computer somebody is using sets every stand-in from
the start, `DIRT_OPENED_TO_FILE=<file>` too (a file's "Open in another app"
writes its path there instead of starting another program on the person's
screen), gives the web view a data folder and a debugging port of its own
(`WEBVIEW2_USER_DATA_FOLDER`, and `--remote-debugging-port` in
`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`), and stops the app by its process
ID. A web view that shares a data folder with a Dirt already running joins
that one's browser process and ignores its own arguments.

The motion check (`docs/ui/motion-check.md`) starts its test copy of the
desktop app that way, with every stand-in above, and stops it by its process
ID. It adds `DIRT_MOTION_BROWSER`, the Edge or Chrome it uses for the
mockup and its sheets when neither is in the usual place.

## Making a note that cannot be synced

D7, A12 and C4 need a note the device cannot read. With two devices in one
account, A and B:

1. Write a note on A and sync both, so that B holds it.
2. Change the note on A and sync A.
3. Before B syncs, change one byte of that note's row on the server:
   `UPDATE notes SET ciphertext = set_byte(ciphertext, 40, get_byte(ciphertext, 40) # 1) WHERE note_id = '<ID>';`
4. Sync B. It lists the note as one it cannot read, and keeps its own copy.
5. Change the note on A again and sync both. B's list is empty again.

## Notes for whoever runs it

- On an emulator, `adb shell input text` drops letters from long text. Type
  a recovery phrase one word at a time.
- A phone's keyboard gives the first word of a phrase a capital letter. The
  phrase is accepted with it.
- Returning to an app syncs only if the last sync was more than 30 seconds
  ago. Wait that long before A11 and D6.
- The desktop app shows nothing to Windows UI Automation while its window
  is minimised.
- A build for a real phone names its processor:
  `dx build --platform android --target aarch64-linux-android`, with
  `DIRT_MOBILE_API_BASE_URL` set to the server. Without `--target` the
  build is for the emulator. `adb install -r` puts it on a phone that has
  USB debugging on.
- Both servers have file storage since 2026-11-13. For trying files with
  no account and no network,
  `cargo run -p dirt-sim --example serve` runs the real server on
  this machine with the storage from `compose.yaml` and a sign-in that
  needs no account; the comment at the top of
  `crates/dirt-sim/examples/serve.rs` says how to sign in and how to have
  two devices on one computer.
